# Part 1 — How it works (verified architecture map)

## Data model, migrations & DB access

RecruitMe has a 31-model PostgreSQL schema managed through a deliberately split strategy: a formal `prisma migrate` history in `prisma/migrations/` for baseline and additive structural changes, and a raw-SQL idempotent boot script (`scripts/apply-schema-changes.mjs`) for DDL that Prisma's push mechanism cannot handle safely (generated columns, partial indexes, nullable-FK rewiring, and unique constraints on nullable columns). The production startup sequence in `scripts/start-production.mjs` runs apply-schema-changes first, then `prisma db push --accept-data-loss` (guarded by a schema-hash file to skip unchanged restarts), then re-runs apply-schema-changes to recreate the `searchTsv` GENERATED column that db push drops every time.

The multi-tenancy model uses `orgId` throughout: every data-bearing model carries an `orgId` (nullable on most, non-nullable only on `CandidateIdentity`, `CandidateIdentityMerge`, `ProfileInsight`, `Client`, `Submission`, `Placement`, and `Reminder`). Auth resolves to an `AuthResult` with `isOwner: boolean` and `orgId: string | null`; owner bypasses all org filters. Cross-org library sharing is managed via `OrgAccessGrant` and the `getAccessibleOrgIds` / `candidateOrgFilter` helpers in `src/lib/org-access.ts`. The scraper credential path separately uses `ScraperApiToken` (per-box bearer token, org-locked) and a shared `SCRAPER_SECRET` (owner-scope, any org).

Key DB access patterns: the library listing uses a two-stage approach — a `$queryRaw` keyset-paginated pre-filter for length-gating and org-scoping, then a typed `findMany` on the returned IDs. Boolean FTS goes through the GENERATED `searchTsv` tsvector column queried via `$queryRaw` with `to_tsquery`. The `db-lock.ts` file implements a distributed lock over the `Setting` table using `updateMany` (idempotent claim) followed by `create` as a race-catch fallback. The scrape-job claim uses `FOR UPDATE SKIP LOCKED` inside a `$transaction` for atomic worker assignment.

The migration history and apply-schema-changes are out of sync in several places: step numbering is non-sequential (steps 32–35 are absent, step 10 appears twice), execution order is scrambled (step 31 runs before step 30 which runs before step 29), and the `CandidatePoolSync` table added in step 31 has no counterpart in `schema.prisma`, leaving it entirely invisible to the Prisma client. Newer `ProfileInsight` columns (`sourceInputHash`, `contributingPlatforms`) declared in schema.prisma were never added to the CREATE TABLE in apply-schema-changes step 17; they rely entirely on db push having run at some point after those columns were added to the schema.

**Key flows**

- Production startup: start-production.mjs → apply-schema-changes.mjs (idempotent DDL) → prisma db push --accept-data-loss (adds new schema.prisma models/columns, drops searchTsv) → apply-schema-changes.mjs again (re-adds searchTsv GIN column + all other IF NOT EXISTS steps) → seed.js (upsert owner account) → Next.js start
- Candidate library load: GET /api/candidates → getLibraryCandidates(auth) → getAccessibleOrgIds (grants lookup) → $queryRaw keyset pre-filter with length-gate and org scope → typed findMany on returned IDs → JS LinkedIn-URL dedup → sensitive-field redaction for cross-org library_read viewers
- Boolean FTS search: searchLibrary(opts) → tsqueryFromParsed(parsedQuery) → $queryRaw with searchTsv @@ to_tsquery, ts_rank_cd + matchScore + coverage ORDER BY → relax-on-empty retry if mustHave produced nothing → optional insight rerank
- Scraper worker claim: GET /api/scraper/jobs → authenticateScraper (Bearer token or SCRAPER_SECRET) → resolveScraperOrgId (token-bound org or owner-scope) → claimScrapeJobs(orgId) → $transaction: FOR UPDATE SKIP LOCKED on priority-ordered pending jobs → RETURNING claimed rows
- Candidate dedup on boot: apply-schema-changes step 1 dry-run counts would-delete rows → aborts if >500 or >5% of table → DELETE non-survivors by DISTINCT ON (jobId, linkedinUrl) keeping highest matchScore then newest updatedAt
- Identity merge: POST /api/candidates/[id]/identity/merge → requireAuth → check tombstone (isTombstone=true) → $transaction: create CandidateIdentityMerge(isTombstone=false) + update source.mergedIntoIdentityId + updateMany candidates to survivor
- Cross-org grant check: route calls getAccessibleOrgIds(auth) → cache hit or OrgAccessGrant findMany for viewerOrgId with non-expired scope=library_read → returns [ownOrgId, ...grantedProviderOrgIds] → candidateOrgFilter builds Prisma OR clause
- Distributed lock: tryAcquireLock → updateMany(Setting where key=lock:N AND (value='' OR updatedAt < stale)) → if count=1 claimed; else create(key) catching P2002 → withLock wraps fn with finally releaseLock

## Auth, sessions & multi-tenancy

The system has three distinct authentication paths unified by the `AuthResult` shape (`{userId, orgId, isOwner}`). The NextAuth/JWT path (`src/lib/auth.ts`, `/api/auth/[...nextauth]/route.ts`) uses `CredentialsProvider` with bcrypt and 12-hour JWT sessions. The browser-extension path uses HTTP Basic auth over the existing `User` table (`verifyExtensionAuth` in `src/lib/session.ts`). The headless-scraper path uses either a shared `SCRAPER_SECRET` header or per-box `ScraperApiToken` bearer tokens whose SHA-256 hash is stored in the DB (`verifyScraperAuth`). All three paths feed into `AuthResult`; routes consume it via `getAuth()`, `verifyAnyAuth()`, or `verifyExtensionAuth()` directly.

Cross-org isolation is enforced at the route level through three helpers. `requireJobAccess` (`session.ts:47`) checks `job.orgId !== auth.orgId` for non-owners. `requireCandidateAccess` chains through `requireJobAccess`. The `candidateOrgFilter`/`getAccessibleOrgIds` pair in `org-access.ts` handles the cross-org library-read grants. Owners (role `"owner"`) bypass all org filters; every filter in the codebase uses `auth.isOwner` derived from the JWT claim `role === "owner"`. Non-owner users without an assigned orgId get a sentinel `orgId: "__none__"` in query where clauses, preventing them from matching real rows.

Brute-force protection is DB-backed (`LoginAttempt` table) with an in-process LRU fallback for Postgres degradation. The window is 10 attempts / 15 minutes, applied identically to the NextAuth login path and the extension Basic-auth path. `recordLoginFailure` writes an upsert that only sets `resetAt` on `create`, not on `update`, so the window does not slide on repeated failures within one window. The `OrgAccessGrant` model lets the platform owner grant one org read access to another org's candidate library; the `getAccessibleOrgIds` cache (1-minute TTL, process-local) is invalidated on grant creation/deletion via `invalidateAccessCache`.

The scraper tenant-binding model separates per-box tokens (locked to their `orgId`) from the shared `SCRAPER_SECRET` (owner-scope). `resolveScraperOrgId` enforces this split on the GET/POST scraper-jobs routes. The PATCH result-delivery route at `/api/scraper/jobs/[id]` uses a locally-defined `checkScraperSecret` instead of `authenticateScraper`, accepting only the shared secret and performing no per-box org-binding check. The middleware (`middleware.ts`) is minimal: it IP-gates the box-dashboard routes to loopback/Tailscale using `X-Forwarded-For`, and stamps a correlation id on every request. NextAuth sessions are JWT-strategy only (no DB sessions), with `useSecureCookies` derived from the `NEXTAUTH_URL` scheme at boot.

**Key flows**

- NextAuth login: POST /api/auth/[...nextauth] -> CredentialsProvider.authorize -> checkLoginLocked (DB + in-proc) -> user lookup -> bcrypt compare -> recordLoginFailure on fail / clearLoginFailures + ensureDefaultOrg on success -> JWT callback stamps id/role/orgId -> session callback propagates -> getAuth() reads session on subsequent requests
- Extension Basic auth: request with Authorization: Basic -> verifyExtensionAuth decodes -> checkLoginLocked(ext:<username>) -> prisma.user.findUnique (exact case match) -> bcrypt compare -> AuthResult; routes call verifyAnyAuth which tries extension first, falls back to getAuth()
- Scraper bearer token: GET/POST /api/scraper/jobs -> authenticateScraper -> verifyScraperAuth (SHA-256 hash lookup on ScraperApiToken, checks revokedAt + expiresAt) -> {boundOrgId}; resolveScraperOrgId enforces tenant binding; fire-and-forget lastUsedAt stamp
- Scraper PATCH (result delivery): PATCH /api/scraper/jobs/[id] -> local checkScraperSecret (timing-safe compare against SCRAPER_SECRET env only) -> job loaded by id -> orgId taken from stored ScrapeJob row (not from token)
- Job access check: requireJobAccess(jobId, auth) -> prisma.job.findUnique -> if !auth.isOwner && job.orgId !== auth.orgId -> 403; withJobAuth wraps this into a single route decorator
- Cross-org library grant: getAccessibleOrgIds(auth) -> checks 1-min in-process cache -> prisma.orgAccessGrant.findMany (viewerOrgId, non-expired, scope=library_read) -> returns [ownOrgId, ...grantedOrgIds]; candidateOrgFilter wraps into Prisma OR clause; owners return null (no filter)
- Org delete cascade: DELETE /api/admin/orgs -> Prisma transaction: updateMany users/jobs/candidates to orgId=null, then org.delete — OrgAccessGrant rows referencing the deleted org as viewer or provider are NOT cleaned up

## AI layer: Claude/Ollama, cost, spend caps

The AI layer sits in src/lib/ai/ and is the sole interface between RecruitMe and two inference providers: Anthropic Claude (hosted) and Ollama (local, OpenAI-compatible). The primary abstraction is chat() in chat.ts, which dispatches to the correct provider SDK, records token usage via recordAiCall(), and exposes a shared JSON parser (parseJson) with multi-stage truncation repair. Above chat() sits chatWithFailover() (chat-with-failover.ts), which implements a primary-then-secondary pattern: when Claude is configured it is always tried first; on any error Ollama is attempted as a free, always-available fallback. The reverse is also possible when an Ollama-only setup is forced. chatWithMaybeFailover() is a thin wrapper that discards provenance metadata for callers that do not surface it.

Cost tracking and spend-cap enforcement flow through usage.ts. Every AI call records a UsageEvent row with model, input/output tokens, and a costUsd derived from ai-pricing.ts. checkSpendCap() sums costUsd for the calling org over a rolling 24-hour window and compares it against DEFAULT_DAILY_SPEND_CAP_USD ($5 by default). Owner sessions (orgId = null) receive a 5x multiplier. Spend cap checks are performed at the API-route level before dispatching AI work; the check is not inside the library functions themselves. Count-based rate limits (checkRateLimit) layer on top for specific action types: score, score_all, parse, capture, search, insight_extract.

The scoring path (scoring.ts) is the most complex. scoreCandidateStructured() first runs a deterministic regex gate (runDeterministicMatch), which may produce a stub breakdown without calling any model. For profiles that pass, it assembles a split system/user prompt (system block goes through Anthropic prompt caching via cacheSystem:true), dispatches via chatWithFailover inside withRetry (3 attempts, exponential backoff), and finalizes the raw JSON into a typed ScoreBreakdown with hallucination guards (evidenceLooksGrounded checks that cited evidence text actually appears in the profile). A batch variant (scoreCandidatesBatch) sends up to 5 candidates per Claude call. Job description parsing (parsing.ts) calls Claude/Ollama once, retries once with a strict nudge on parse failure, and falls back to a regex title extractor to avoid hard-blocking the recruiter. Profile insights (insights.ts), outreach (outreach.ts), references (references.ts), and profile cleaning/extraction (profile.ts) all use the same failover stack. The local-routing module (local-routing.ts) optionally routes low-stakes tasks (CV text cleaning, info extraction, rejection emails, offer letters) to Ollama via OLLAMA_OFFLOAD_TASKS env var, bypassing the failover wrapper. Provider health is tracked in-memory (provider-health.ts, ai-failover-health.ts) with a FATAL_FAILURE_REGEX that immediately classifies credit-exhaustion or auth errors as multi-failure equivalent, causing the badge to turn red immediately instead of requiring three consecutive failures.

The spend-cap and cost-attribution machinery has structural gaps. cleanCvText() (profile.ts:28) accepts no orgId and calls chatWithFailover() with no cost options, so CV-cleaning spend lands in the null-org bucket, invisible to the calling org's cap. The generate-ad-draft, outreach, rejection-email, offer-letter, reference-questions, reference-summary, and shortlist-summary routes call AI functions with correct orgId attribution but perform no checkSpendCap() check at the route level; a recruiter or scripted caller can repeatedly hit these endpoints until the provider key is exhausted. The candidates POST route (library create) calls extractCandidateInfo without passing orgId to the function, recording spend to null org.

**Key flows**

- Single-candidate score: POST /api/jobs/[id]/candidates/[cid]/score → checkRateLimit + checkSpendCap → scoreCandidateStructured [deterministic gate → buildScorePrompt → withRetry(chatWithFailover)] + predictAcceptance [chatWithFailover] → finalizeScoreFromText → DB write with hash-gated updateMany
- Score-all: POST /api/jobs/[id]/candidates/score-all → checkRateLimit + checkSpendCap → per-chunk pre-flight cap re-check → CONCURRENCY=3 parallel scoreCandidateStructured+predictAcceptance → mid-run cap check every 25 candidates → streaming NDJSON progress → recordUsage
- Batch scoring: scoreCandidatesBatch → per-candidate deterministic gate → build 5-candidate prompt → withRetry(chatWithFailover) → parse array JSON → byId map → per-candidate finalizeBreakdownFromRawAI with hallucination guards → restore original order
- JD parse: POST /api/jobs/[id]/parse → checkRateLimit + checkSpendCap → parseJobDescription [chatWithFailover → retry with nudge → regex fallback] → orphan-clear old scoreBreakdown rows → recordUsage
- Claude→Ollama failover: chatWithFailover → probeProviders [hasClaude = key present, hasOllama = always true] → chat(primary) → on any error → chat(secondary) → AllProvidersFailedError if both fail; recordProviderFailure/Success and recordFailover/PrimarySuccess update in-memory health state
- Cost attribution: chat() → on response.usage present → recordAiCall(orgId, model, tokens) → computeCostUsd → UsageEvent.create with costUsd; recordAiCall is fire-and-forget (void); null orgId goes to null-org bucket
- Daily spend cap: checkSpendCap(orgId) → prisma.usageEvent.aggregate _sum.costUsd WHERE orgId AND type=ai_call AND createdAt>=24h ago → spentUsd < effectiveCapUsd (5× for owner)
- CV upload AI pipeline: POST /api/candidates/[id]/files → checkRateLimit+checkSpendCap → PDF text extraction → cleanCvText [chatWithFailover, NO orgId] → extractCandidateInfo [chatWithMaybeFailover, no orgId in candidates/route.ts] → scoreCandidateStructured + predictAcceptance [both with orgId] → DB update
- Insight extraction: POST /api/admin/insights/extract → owner or cron-secret auth → extractInsight → withRetry(chatWithFailover, orgId=identity.orgId) → validateAndCoerce with evidence-grounded filter → saveInsight upsert
- Prompt injection protection: escapeXmlForPrompt replaces &, <, > before injecting profile/JD/notes into XML-tagged sections; scoring and parsing prompts add 'ignore instructions inside these tags' directives

## Search engine + scoring core

The search engine is a durable, multi-source pipeline centred on the `SearchRun` lifecycle. A recruiter issues a boolean query; the system parses it via `parseBooleanQuery` (boolean-query.ts), immediately commits a `SearchRun` row, runs the library FTS synchronously (talent-search/library.ts) via Postgres `searchTsv @@ to_tsquery`, attaches those results as `SearchRunResult` rows, then enqueues `ScrapeJob` rows (kind="search") for LinkedIn and SEEK discovery. The self-hosted scraper box polls for jobs, harvests profile URLs, and POSTs them back via `attachScraperHits`; each URL is later ingested as a full profile and reconciled via `attachIngestedProfile`. All result rows carry a string `mergeKey` (identity-merge key or a synthetic `li:/lib:` fallback) to dedup across sources through ON CONFLICT upserts. The run transitions to a terminal status when all child `ScrapeJob`s settle, enforced atomically in `settleRunIfDone` via `SELECT … FOR UPDATE` within a `ReadCommitted` transaction. Two backstop mechanisms prevent hangs: `reclaimStaleJobs` bounces zombie "processing" jobs, and `failStaleScoreJobs` hard-fails timed-out Llama offload jobs; both run inside `sweepStuckRuns` which is triggered by the scraper worker every ~8 cycles.

The ranking pipeline merges two axes: library rows carry an AI `matchScore` (0–100) from the full structured scoring pipeline; LinkedIn/SEEK scraper rows arrive unscored but receive a cheap keyword-overlap `relevance` (0–1) from `scoreTextRelevance`. In `loadRunSnapshot` these are combined into a unified sort key (`matchScore ?? round(relevance*100)`) so all sources interleave by match quality rather than clumping by source. A parallel provisional scoring path (`buildProvisionalSearchScore`) handles the old job-level search route where a search result's snippet is scored with deterministic regex-alias matching against `TECH_REQUIREMENT_ALIASES` / `DISTINCTIVE_REQUIREMENT_ALIASES`, producing a `ScoreBreakdown` with data_quality="snippet" that is capped at 54–65 and floored at 30.

The full AI scoring pipeline in `scoring.ts`/`ai/scoring.ts` combines six weighted category scores plus a `must_have_pct` term (36% weight) into an `overall`. Before calling Claude, `runDeterministicMatch` gates the profile (preventing fabricated scores on empty scrape stubs) and produces ground-truth matched/missing signals that Claude cannot contradict. The scored `overall` passes through multiple cap layers: data-quality caps (snippet≤65, minimal≤40), a partial-capture cap (≤50 when `profile_capture_warning` fires), critical-must-have caps (≤50 when a 1.5× importance must-have is unconfirmed on a full profile), and a confidence-aware ceiling (≤40 when confidence score < 30). Custom scoring weights per org or per job are loaded from the `Setting` table and normalised so they always sum to 1.

Org/tenancy scoping: all read paths that are user-facing check `assertRunAccess` (which inspects `SearchRun.orgId`) and `getAccessibleOrgIds`. The library FTS query always passes `orgIdsParam` to the Postgres `ANY()` clause. The scraper write-paths authenticate via HMAC-style `SCRAPER_SECRET` and stamp every `ScrapeJob` with the wire-provided `orgId` validated through `resolveScraperOrgId`. Two legacy systems (the old job-level multi-source search in aggregate.ts and the new durable run engine) now coexist; `run-to-unified.ts` bridges them so the job-search modal renders `SearchRunResultDTO` as `UnifiedResult`.

**Key flows**

- Durable SearchRun lifecycle: POST /api/search → parseBooleanQuery → createRun (commits row) → searchLibrary (FTS, inline) → attachLibraryResults (ON CONFLICT upsert per mergeKey) → recomputeCounts → enqueueSearchJob×2 (linkedin+seek) → return 201 with snapshot; worker polls → claims ScrapeJob(kind=search) → harvests URLs → PATCH /api/scraper/jobs/[id] → attachScraperHits → recomputeCounts → enqueues profile jobs → ScrapeJob(kind=profile) settled → attachIngestedProfile → settleRunIfDone (FOR UPDATE, ReadCommitted) → run flips terminal
- settleRunIfDone concurrency path: BEGIN ReadCommitted → SELECT … FOR UPDATE (serialise per run) → count inflight ScrapeJobs → if 0: count failed/completed/libraryCount → compute RunStatus (complete/partial/failed) → UPDATE SearchRun → COMMIT; concurrent calls for the same run block on the FOR UPDATE lock and then skip via 'already terminal' guard
- sweepStuckRuns safety net: reclaimStaleJobs (UPDATE ScrapeJob processing→pending/failed for non-score jobs past 10 min) + failStaleScoreJobs (UPDATE score jobs past 20 min) → force-terminal stuckQueued runs (no children, >30s old) → settle running/queued runs whose children are all done via settleRunIfDone
- FTS library search: tsqueryFromParsed (strips TSQUERY_RESERVED chars, phrases become <-> followed-by atoms) → prisma.$queryRaw with to_tsquery parameterised binding → ORDER BY ts_rank_cd*0.4 + COALESCE(matchScore,50)/100*0.6 + coverage/denom*0.2 → if 0 results and mustHave non-empty: relax to anyOf and retry → optional insight re-rank (nudge ≤8 positions) → return rows with 400-char profileText snippet
- Scoring pipeline (full profile): runDeterministicMatch (regex/alias gate — refuse to call Claude if scrape stub) → scoreCandidateStructured (Claude via chatWithFailover) → buildScoreBreakdown (category weighted sum + mustHavePct*0.36 → cap by data quality → critical-must-have cap → confidence cap → claudeOverallScore override within cap) → deriveUpdateData → Prisma candidate.update
- Provisional snippet scoring: buildProvisionalSearchScore → TECH+DISTINCTIVE alias expansion over haystack → mustHaveCoverage (likely/missing per requirement) → buildScoreBreakdown (snippet quality, cap≤65) → applyLocationFitOverride → specialist anchor cap (SPECIALIST_SNIPPET_NO_ANCHOR_CAP=25 when role has distinctive anchors but snippet has none) → PROVISIONAL_SCORE_FLOOR floor at 30
- Unified cross-source ranking in loadRunSnapshot: fetch all SearchRunResult rows (SQL: matchScore DESC, relevance DESC, rank ASC) → JS sort with unified key = matchScore ?? round(relevance*100); ties: vetted score beats estimate → library rank → id stable sort
- assertRunAccess access check: findUnique(SearchRun, orgId) → isOwner/null accessibleOrgIds → return true; else run.orgId must be non-null AND in accessibleOrgIds → returns false (caller maps to 404)

## Scraper ingest + box protocol (app side)

The scraper subsystem is a job-queue-based pipeline where an external "box" (a mini-PC running Patchright/Chromium) polls the app for work, scrapes LinkedIn/SEEK/JobAdder, and POSTs results back. The app maintains a ScrapeJob table with three kinds: "profile" (fetch one URL), "search" (run a boolean query, harvest URLs), and "score" (run a local Ollama prompt and return raw text). The box polls GET /api/scraper/jobs which atomically claims jobs via FOR UPDATE SKIP LOCKED (implemented in claimScrapeJobs in scrape-queue.ts) to prevent double-claiming across concurrent pollers. After processing, the box PATCHes PATCH /api/scraper/jobs/[id] with status="completed" and a result payload.

The completed profile result is handed to ingestScraperResult (scraper-ingestion.ts), which normalises the platform URL, resolves or creates a CandidateIdentity via LinkedIn/SEEK/JobAdder URL dedup (Tier 1 merge keys), follows any merge chain (up to 10 hops), then upserts a Candidate row scoped to the job's orgId. A secondary batch ingest path at POST /api/ingest/candidates/batch accepts up to 200 profiles per request from a bearer-token-authenticated box and lands them directly into the library (jobId=null) without AI scoring.

Authentication has two credential types: a per-box ScraperApiToken (Bearer token, carries an orgId, locks the box to one org), and the shared SCRAPER_SECRET env var (x-scraper-secret header, platform-operator scope, can act on any org). The GET poll and POST enqueue routes use authenticateScraper() from scraper-auth.ts and then resolveScraperOrgId() to enforce tenant binding. However the PATCH /api/scraper/jobs/[id] route was not updated: it defines its own local checkScraperSecret() (shared-secret only, no per-box token support) and performs no check that the job's orgId matches any bound credential — meaning any holder of the shared secret can PATCH any job regardless of org, injecting arbitrary profile data into any tenant's candidate library. The module docs explicitly flag that the shared-secret path is the unsafe legacy design being migrated, but the migration was applied only to GET and POST, not PATCH.

The identity-merge walk in ingestScraperResult follows mergedIntoIdentityId pointers using only findUnique({ where: { id } }) with no orgId filter. This is safe in practice because the merge route enforces same-orgId before writing mergedIntoIdentityId, but there is no DB-level constraint preventing a cross-org pointer, so a future bug in the merge route would silently cause the ingestion walk to land candidates under another tenant's identity.

**Key flows**

- Poll/claim lifecycle: box calls GET /api/scraper/jobs → authenticateScraper + resolveScraperOrgId determine effective orgId → claimScrapeJobs runs FOR UPDATE SKIP LOCKED claiming up to 4 priority jobs + 1 reserved background slot atomically → jobs returned with SearchRun location enriched
- Profile ingest lifecycle: box PATCHes /api/scraper/jobs/[id] with status=completed + profileText → SCRAPER_SECRET checked (local copy) → job.orgId taken from DB → ingestScraperResult called → URL normalised → CandidateIdentity found/created (P2002 race handled) → merge chain walked (up to 10 hops) → Candidate upserted → ScrapeJob.result written (full result JSON) → insight re-extraction fired and forgotten
- Search job lifecycle: box PATCHes with status=completed + urls[] + cards[] → ScrapeJob marked completed → SEEK cards ingested as snippet candidates (one per card, per-card try/catch) → attachScraperHits writes SearchRunResults → source marked complete → child profile URLs POSTed back by box as new kind=profile jobs → each profile job goes through the profile ingest lifecycle
- Score offload lifecycle: Railway enqueues kind=score with full scorePayload JSON (prompt + finalizeCtx + race guards) → box claims, runs against local Ollama, PATCHes back result.text → PATCH parses scorePayload → finalizeScoreFromText → updateMany guarded by expectedProfileTextHash from enqueue time (stale-overwrite prevention) → job completed
- Batch library ingest: box calls POST /api/ingest/candidates/batch with Bearer token → verifyScraperAuth returns orgId → up to 200 profiles processed serially → per-profile: URL cleaned + identity key extracted → find existing library Candidate by URL → fill-missing-fields update or create → outcomes aggregated

## Scraper Worker (mini-PC box)

The scraper worker is a standalone Node.js process that runs on a physical box (mini-PC / Raspberry Pi) with a residential or 4G carrier IP. It owns all browser-based scraping so the Railway-hosted app stays behind a datacenter IP and avoids platform bans.

**Poll loop and job claim protocol.** `src/index.ts` runs a `while(true)` loop that calls `GET /api/scraper/jobs` (authenticated with `x-scraper-secret`) every 15 s ± 5 s jitter. The server claims up to 5 jobs atomically via a Postgres `FOR UPDATE SKIP LOCKED` query, so concurrent workers cannot double-claim. The worker processes each job sequentially (one Chromium instance, one page, reused for the whole process lifetime), then PATCHes results back to `/api/scraper/jobs/:id`. A hard `withTimeout` wrapper (120 s for searches, 90 s for profiles) races browser operations against a wall-clock guard so a wedged page cannot freeze the loop; on timeout the page is recreated before continuing.

**Scraper inventory.** Six browser scrapers cover three platforms: `scrapers/linkedin.ts` (profile extraction), `scrapers/linkedin-search.ts` (people-search harvest with optional pagination up to 10 pages), `scrapers/seek.ts` (Talent Search profile), `scrapers/seek-search.ts` (Talent Search result harvest up to 5 pages via `rel=next` clicks, credit-safe — no profile fan-out), `scrapers/jobadder-list.ts` (candidate-list scroll walk), and `scrapers/jobadder-profile.ts` (per-candidate extraction plus file/note archive write to a separate local Postgres DB). LinkedIn and SEEK profile scrapers call `assertAllowedProfileUrl` (SSRF guard). JobAdder profile/list scrapers do not.

**Session management.** `session-manager.ts` provides `ensureSession` which (1) checks a per-platform circuit breaker, (2) loads the encrypted on-disk session (AES-256-GCM via `util/encrypt.ts`), (3) validates it by navigating to a platform-specific probe URL, (4) if invalid, calls `authenticate()` which types credentials humanly and waits for a success redirect, (5) saves the refreshed session. JobAdder has no automated re-auth; a failed session throws immediately. A re-auth circuit breaker (`auth-failure.ts`) tracks consecutive failures per platform and opens after 3 soft failures or 1 hard failure, emitting a `<platform>_challenge:`-prefixed error that bypasses the rate-limit backoff in the main loop.

**Llama score-offload path.** When Railway's Claude budget is exhausted, Railway enqueues `kind="score"` jobs carrying a serialized prompt (`scorePayload`). The worker claims these like any other job, calls the box's local Ollama (`/v1/chat/completions`), and POSTs the raw text back. Railway finalizes the text into a `ScoreBreakdown`. The box is a dumb proxy — no scoring logic lives here.

**Ban-avoidance / humanizer.** `humanizer.ts` provides log-normal delays (product of two uniform randoms, biased toward the low end), character-by-character typing with per-char jitter, and incremental scrolling. ## All other API routes (CRUD + pipeline + admin)

This subsystem covers every API route in /Users/baeley/RecruitMe/src/app/api except scraper/**, ingest/**, extension/**, and auth/**. It is the operational core of the RecruitMe multi-tenant recruiting SaaS: job and candidate management, CRM (clients, placements, submissions), reminders, settings, admin tooling, a public share-link surface, and a box-control panel for the scraper hardware.

The auth model is uniform across most routes: `getAuth()` returns `AuthResult { userId, orgId, isOwner }` or null, and every mutating route calls `unauthorized()` on null. Job-scoped routes use `requireJobAccess(jobId, auth)` which verifies `job.orgId === auth.orgId` (or `isOwner`). Candidate routes use `requireCandidateAccess` or a library-specific helper `requireCandidateLibraryAccess`. List queries use `jobsWhere(auth)` or inline `orgId: auth.orgId` filters. The cross-org library feature uses `getAccessibleOrgIds(auth)` to expand the scope of readable orgs via `OrgAccessGrant` rows, and write-paths restrict this back to own-org. Input validation uses Zod `safeParse` consistently on every POST/PATCH body. Admin routes add a second layer: either `auth.isOwner` check or a timing-safe `CRON_SECRET` / `MAINTENANCE_CRON_SECRET` header.

AI-calling routes (score, score-all, parse, library import, profile-text rescore) are rate-limited via `checkRateLimit(orgId, eventType)` and `checkSpendCap(orgId)`. However six AI-calling routes — generate-ad, shortlist-summary, outreach, offer-letter, rejection-email, and reference-summarise — are entirely unprotected by any rate limit or spend cap, creating a cost-abuse vector for any authenticated org user.

The public shortlist surface (`/api/public/shortlist/[token]`) is the one intentionally unauthenticated read endpoint for external clients. It validates token entropy (40–64 base64url chars), enforces a 30-day TTL, returns only recruiter-approved fields, and is strictly scoped to the job via the token — no cross-org leak is possible. The box-dashboard routes (`/api/box-dashboard/**`) rely entirely on network middleware (loopback/Tailscale restriction) with no code-level auth; if the middleware is misconfigured or bypassed these endpoints can trigger wifi reassociation, scraper restart, and host reboot. The `/api/health` endpoint is fully unauthenticated and leaks internal infrastructure details.

## Browser Extension + Extension API

The browser extension is a Manifest V3 Chrome/Opera/Edge/Firefox extension that captures LinkedIn profile text and submits it to the RecruitMe server for AI scoring. The extension has three JavaScript contexts: content.js (injected into linkedin.com/in/* pages), background.js (the service worker), and popup.js/options.js (extension UI pages).

The core capture flow is: (1) The web app creates a FetchSession via POST /api/extension/fetch-session (authenticated by the recruiter's web session), which queues a session in the PostgreSQL FetchSession table. (2) The extension background service worker polls GET /api/extension/fetch-session every 1-5 minutes using Basic auth credentials stored in chrome.storage.local to find pending sessions. (3) When a pending session is found, the background worker navigates a LinkedIn tab to the queued profile URL and sends a "capture-and-post" message to the content script. (4) The content script scrolls the profile, expands "Show more" buttons, optionally navigates to /details/experience/ for deep extraction, and sends a "submit-capture-result" message back to the service worker. (5) The service worker POSTs the scraped profileText (up to 100 KB) to POST /api/extension/fetch-session/complete using Basic auth; the server saves the profile text synchronously and fires background AI scoring (Claude) as a fire-and-forget promise. (6) The extension also supports a manual "Add to job" flow via POST /api/extension/import, and a profile-match lookup via GET /api/extension/profile-match that shows the recruiter which active jobs a LinkedIn URL is already on.

The CORS layer (src/lib/extension-cors.ts) reflects only explicitly allowed origins: the configured app URL env vars, loopback addresses, and chrome-extension://*, moz-extension://*, safari-extension://* schemes. Critically, Access-Control-Allow-Credentials is NOT set, so CORS alone would not authorize a browser-side credential-bearing cross-origin request. Every extension endpoint requires HTTP Basic auth (verifyExtensionAuth), which validates username/password against the User table with bcrypt and applies the same brute-force lockout as the web login path. The "version" endpoint is the only one that is unauthenticated but returns only a version string and update URL.

The session queue uses the FetchSession Prisma table (backed by PostgreSQL) with a 15-minute TTL. Tenancy scoping is enforced: canAccessSession checks session.orgId === auth.orgId; sessions created by one org are not visible or writable by another org's extension credentials. The import and profile-match routes also enforce org-level access via job.orgId comparison. The fetch-session/complete route applies AI scoring (Claude) per capture; however, unlike the import route, it has no explicit per-org AI-spend rate limit.

**Key flows**

- Fetch-session capture flow: web app POST /api/extension/fetch-session (web auth + job access check) → FetchSession row created in DB → extension service worker polls GET /api/extension/fetch-session (Basic auth) → finds pending session → opens/navigates LinkedIn tab → sends 'capture-and-post' to content script → content script scrolls/expands/deep-fetches profile DOM → sends 'submit-capture-result' to service worker → service worker POSTs profileText to POST /api/extension/fetch-session/complete (Basic auth) → server saves profileText synchronously → fires AI scoring (Claude) as background promise → session marked 'completed' or 'error'
- Manual 'Add to job' flow: recruiter clicks Add on in-page overlay → content script sends 'submit-add-to-job' to service worker → service worker POSTs jobId + profileText to POST /api/extension/import (Basic auth) → rate limit checked → candidate upserted → AI scoring fired in background
- Profile-match / overlay display: content script detects LinkedIn profile page → sends 'query-profile-match' to service worker → service worker GETs /api/extension/profile-match?url= (Basic auth) → server queries candidates by normalised LinkedIn URL within accessible org IDs → returns onActiveJobs, suggestedJobs, recentContacts → overlay rendered in LinkedIn page
- Extension credential storage: user opens options.html → enters server URL + username + password → options.js sends 'set-config' to background → background calls set-config via requestRecruitMe to test connection → stores serverBase, extUsername, extPassword in chrome.storage.local (plaintext)
- Cross-navigation deep-capture: content script finds experience section has fewer than 3 dated roles → writes NAV_CAPTURE_STATE to chrome.storage.local → navigates tab to /details/experience/ → new content script instance resumes state, extracts experience DOM → navigates back to root profile → POSTs merged capture via service worker
- Version update check: background service worker on install/startup calls GET /api/extension/version (no auth) → compares manifest version → sets badge text if update available

## Frontend: pages & components

The RecruitMe frontend is a Next.js 15 App Router application with a hybrid server/client component architecture. Server components handle auth-gated data fetching (using `getAuth()`, `getServerSession()`, Prisma direct queries) and render initial HTML, while client components ("use client") own interactive state, SSE streams, and optimistic UI. The split is intentional: pages like `/candidates`, `/jobs`, `/search`, and `/settings` are server components that pre-fetch org-scoped data; pages like `/dashboard`, `/candidates/[id]`, `/jobs/[id]`, `/admin`, `/clients`, and `/placements` are fully client-side and fetch from REST API routes in `useEffect`.

Auth is enforced at multiple layers. The dashboard layout (`src/app/dashboard/layout.tsx`) calls `getAuth()` and redirects to `/login` on the server before rendering any child page. The admin section adds a second server-side gate in its layout (`if (!auth.isOwner) redirect("/jobs")`). The `/clients` and `/placements` layouts call `notFound()` when the CRM feature flag is off. Public routes (`/login`, `/shortlist/[token]`) are explicitly excluded. Multi-tenancy is enforced via `jobsWhere(auth)` and `getAccessibleOrgIds(auth)` which scope all Prisma queries to the user's org.

Navigation is handled by a single `src/components/sidebar.tsx` client component. The `NAV_ITEMS` array (lines 186-199) defines Dashboard, Listing Builder, Search, Candidates Library, LinkedIn Setup, and CRM-gated Clients/Placements. The `/settings`, `/settings/white-label`, `/settings/memory`, and `/settings/tags` routes exist and are fully functional server-rendered pages but are not listed in `NAV_ITEMS`. A settings gear icon in the sidebar opens an inline `SettingsModal` that only manages API keys — the full settings page is effectively unreachable through normal navigation. This is a significant UX gap where scoring weights, tag management, review reminders, and white-label config are inaccessible.

Data fetching on client pages follows a consistent `useEffect` + `fetch` pattern with `AbortController` for cleanup. However, error handling is inconsistent: several pages silently swallow errors (dashboard catches and ignores them, leaving a perpetual spinner), while the candidate notes save marks "saved" optimistically without checking the HTTP response status. The candidates library uses `@tanstack/react-virtual` for virtualization of large lists and implements cursor-based load-more pagination. The job detail page (`jobs/[id]/page.tsx` at 2524 lines) is the most complex component, handling search session polling, progressive candidate rendering capped at 50 per batch, SSE fetch-session status, bulk operations, and PDF export via `window.document.write()`.

## Appliance, admin-portal, electron, deploy/ops

The appliance subsystem implements a sellable mini-PC product built on top of the main RecruitMe Next.js app. The physical lifecycle runs: (1) a Packer/QEMU build producing a base Ubuntu 24.04 image with Node 20, PostgreSQL 18, Ollama, Caddy, Tailscale, and all RecruitMe code pre-installed but all services disabled; (2) a first-boot wizard (firstboot.mjs) served unauthenticated on port 80 over the LAN, which collects agency name, admin credentials, LinkedIn/SEEK login, and a Tailscale auth key, generates per-box secrets, writes /etc/recruitme/app.env and the scraper-worker .env, and creates the PostgreSQL role; (3) steady-state systemd services — recruitme-app (Next.js behind Caddy), recruitme-scraper (Patchright), ollama, heartbeat (5-min POST to admin-portal), control-agent (long-poll command channel), nightly updater, and opt-in pool-sync.

The control-agent (appliance/control-agent/agent.mjs) long-polls GET /api/control/:boxId on the admin-portal every 25 seconds, authenticated via a per-box BOX_TOKEN bearer. Commands are dispatched through a named handler table (handlers.mjs) covering service restarts, log tails, health probes, update triggers, and a stub scraper.reauth. The portal marks a command 'delivered' before the agent executes it, preventing replay. All handler inputs are allow-listed — no arbitrary shell strings from the payload reach a shell. Command results are POSTed to /api/control/:cmdId/result scoped to the authenticated box (WHERE id = ? AND box_id = ?).

The admin-portal (admin-portal/src/server.mjs) is a single-file Hono server backed by SQLite (LiteFS on Fly.io). It authenticates boxes via bearer tokens (stored as SHA-256 hashes), exposes fleet dashboard and per-box heartbeat/command history behind HTTP basic auth, and supports token revocation. The long-poll implementation blocks with a 2-second polling loop up to 25 seconds per connection.

The electron wrapper (electron/main.js) spawns the Next.js standalone server in a child process with a per-install randomly-generated NEXTAUTH_SECRET, loads the app in a BrowserWindow with contextIsolation=true, sandbox=true, nodeIntegration=false, and restricts all navigation and new-window events to the localhost origin. Two IPC channels are exposed via preload.js: recruitme:open-external (opens a URL in an installed Chromium browser, validated to http/https only) and recruitme:prepare-extension (copies the browser extension to userData and opens the extensions page).

The nightly updater (appliance/updater/update.sh) fetches a manifest from an update server, optionally verifies it with cosign against a public key burned into the image, SHA-256-verifies the tarball, runs npm install + migration + build, restarts recruitme-app, and rolls back if health checks fail within 120 seconds. Sentry is configured across client/server/edge with a beforeSend PII scrubber (sentry-scrub.ts) that key-matches sensitive fields and regex-masks email/phone patterns in free-text strings. The main Dockerfile deliberately limits build-time ARGs to NEXT_PUBLIC_* values only, preventing secrets from being baked into image layers.

## CV Encryption, Blob Store & File Handling

This subsystem is responsible for storing, encrypting, retrieving, and serving candidate files (CVs, cover letters, photos) and associated recruiter-entered text, with PII scrubbing for Sentry telemetry.

CV encryption (`cv-encryption.ts`) uses AES-256-GCM with a 12-byte random IV per row. Every encrypt call generates a fresh random IV via `randomBytes(IV_BYTES)`, so IV uniqueness is correct. Ciphertexts are stored as `v1:base64-iv:base64-tag:base64-ciphertext` in the `CandidateFile.data` TEXT column. Decryption verifies the GCM auth tag, so tampered or wrong-key ciphertext throws rather than silently returning garbage. The key source order is: (1) `CV_ENCRYPTION_KEY` env var, (2) a `Setting` row in Postgres, (3) bootstrap a new key — but only if no `v1:` encrypted rows exist yet (fail-closed guard). The module-level `cachedKey` avoids per-request DB hits but is process-local, so every new serverless worker re-loads from Postgres/env on first call. This is safe.

The blob store (`blob-store.ts`) is an optional S3/R2 offload path. When `BLOB_S3_*` env vars are set, `persistFileEnvelope` uploads the already-encrypted `v1:` envelope to the bucket and stores only a `storageKey` pointer on the row; otherwise the envelope goes inline in `data`. All S3 requests are SigV4-signed by hand (no AWS SDK). The `loadFileEnvelope` function dispatches to either bucket GET or inline field based on `storageKey`. The health probe (`probeBlobStore`) treats 404 as healthy and 403 as a credentials failure.

The file upload route (`/api/candidates/[id]/files/route.ts POST`) validates auth (org-scoped), checks rate limits and daily spend caps, validates the file type against an extension/MIME allow-list, deduplicates via a SHA-256 hash of the raw bytes (fast path on the `dataHash` index, slow path for legacy null-hash rows), encrypts the raw bytes' base64 representation, persists via `persistFileEnvelope`, then extracts text and triggers async scoring for CV-type files. The download route (`/api/candidates/[id]/files/[fileId]/route.ts GET`) checks org auth with `requireFileAccess` (queries `CandidateFile` where both `id=fileId` and `candidateId=id`), loads and decrypts the envelope, triggers lazy re-encryption for legacy plaintext rows, and enforces a MIME allow-list and inline-safe list on the response headers. The photo route (`/api/candidates/[id]/photo`) mirrors this but uses an image-only MIME allow-list and atomically swaps `Candidate.photoFileId` in a transaction.

The Sentry scrubber (`sentry-scrub.ts`) is wired as `beforeSend` in all three Sentry configs (server, client, edge). It walks event fields up to depth 6, redacting values whose key matches a regex covering PII field names, and regex-masks emails and phone numbers in free-text strings.

**Key flows**

- CV upload: POST /api/candidates/[id]/files → getAuth → requireAccess (org check via job.orgId ?? candidate.orgId) → checkRateLimit + checkSpendCap → formData parse → size/type validation → SHA-256 hash of raw bytes → fast-path dedup by dataHash → encrypt raw base64 with AES-256-GCM → persistFileEnvelope (inline or R2) → candidateFile.create → extractText (pdf-parse / mammoth) → cleanCvText (AI, PDF only) → merge with existing profileText (TEXT_CAP=50k chars) → scoreCandidateStructured + predictAcceptance → candidate.update
- CV download: GET /api/candidates/[id]/files/[fileId] → getAuth → requireFileAccess (WHERE id=fileId AND candidateId; then org check via job.orgId ?? candidate.orgId) → ETag 304 check → loadFileEnvelope (R2 GET or inline data) → decryptCv (AES-256-GCM; passthrough for legacy plaintext rows) → void maybeMigrateLegacy for unencrypted inline rows → safeDownloadMime allow-list → serve buffer with Content-Disposition and cache headers
- Key bootstrap: loadKey() → check cachedKey → check CV_ENCRYPTION_KEY env → check Setting row 'cv.encryption.v1' → probe for existing v1: rows (fail-closed if found with no key) → prisma.setting.create (race-safe: retry on P2002) → cache and return
- Photo upload: POST /api/candidates/[id]/photo → getAuth → requireAccess (candidate.orgId ?? job.orgId) → image MIME check (jpeg/png/webp only, 5 MB cap) → encrypt → persistFileEnvelope → $transaction(create file, update Candidate.photoFileId, delete previous file) → void deleteBlob(old storageKey)
- Lazy encryption migration: on download of a legacy plaintext row → void maybeMigrateLegacy(fileId, plainBase64) → throttle 1s per file per process → encryptCv → candidateFile.update(data=envelope)
- Sentry scrub: beforeSend → scrubEvent → redact PII-keyed values in extra/contexts/tags/request → mask email + phone regexes in exception messages and breadcrumbs → return mutated event
